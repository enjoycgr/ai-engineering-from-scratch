# SRE for AI — 多智能体事件响应、运维手册与预测性检测

> AI SRE 通过 RAG 将 LLM 与基础设施数据（日志、运维手册、服务拓扑）结合，实现调查、文档和协调阶段的自动化。2026 年的架构模式是多智能体编排——由监督器协调的专用智能体（日志、指标、运维手册）；AI 提出假设和查询，人类审批判断。Datadog Bits AI 和 Azure SRE Agent 已将其作为托管产品推出。运维手册正在演进：NeuBird Hawkeye 使用对抗性评估（两个模型分析同一事件；一致=高置信度，不一致=升级）；运维记忆（operational memory）在团队变动时持续保留。自动修复保持谨慎：AI 建议，人类审批。完全自主的行动范围很窄（重启 Pod、回滚特定部署）且受严格护栏约束——任何兜售"设置好就不用管"的人都在过度推销。新兴前沿：预事件预测。MIT 研究报告称，一个在历史日志 + GPU 温度 + API 错误模式上训练的 LLM 能在 89% 的故障发生前 10-15 分钟预测到。预测：到 2026 年底，95% 的企业 LLM 将实现自动故障转移。

**类型：** Learn
**语言：** Python（stdlib，玩具级多智能体事件分类模拟器）
**前置条件：** Phase 17 · 13（可观测性），Phase 17 · 24（混沌工程）
**时间：** ~60 分钟

## 学习目标

- 绘制多智能体 AI SRE 架构图：监督器 + 专用智能体（日志、指标、运维手册）+ 人类审批关卡。
- 解释为什么自动修复范围很窄（重启 Pod、回滚部署）而不是很广（重构服务）。
- 说出对抗性评估模式（NeuBird Hawkeye）：两个模型一致=高置信度；不一致=升级。
- 引用 MIT 89% 早期检测成果及运维约束：没有执行动作的预测只是仪表盘。

## 问题

一名值班工程师在凌晨 3 点收到告警。"结账错误率高。"他们检查 Datadog、Loki、三本运维手册、部署日志。30 分钟后发现根本原因是 vLLM 因 KV cache（KV 缓存）激增导致 OOM。他们重启了 Pod，错误清除。

在 2026 年，这段调查的前 20 分钟可以自动化。按服务分组日志、关联近期部署、匹配运维手册——这些都是 RAG + 工具使用。有监督的智能体可以在人类打开 Datadog 之前完成初步分类并呈现假设。

完全自主修复是另一个问题。重启 Pod：安全。扩展 GPU 池：如果策略允许则安全。重构服务：绝对不行。这门学科在于划定那条狭窄的界限。

## 概念

### 多智能体架构

```
          Incident
             │
             ▼
        Supervisor
        /    |    \
       ▼     ▼     ▼
  Log agent  Metric agent  Runbook agent
       │     │     │
       └─────┴─────┘
             │
             ▼
        Hypothesis + evidence
             │
             ▼
        Human approval
             │
             ▼
        Action (narrow set)
```

监督器将事件拆分为子查询。专用智能体拥有工具访问权限（日志搜索、PromQL、文档检索）。监督器综合结果，向人类呈现假设 + 证据。人类审批或重定向。

### 自动修复范围

**安全（窄范围）**：重启 Pod、回滚特定部署、在预批准范围内扩展池、启用预批准的功能开关。

**不安全（广范围）**：更改服务拓扑、修改资源限制、部署新代码、更改 IAM、修改数据库。

任何兜售"设置好就不用管"的人都在过度推销。随着 AI SRE 成熟，安全集会扩大，但边界是真实存在的。

### 对抗性评估（NeuBird Hawkeye）

两个模型独立分析同一事件。如果它们在根本原因上达成一致，置信度就高。如果它们不一致，就向人类升级并展示两个假设。简单的模式，有效过滤幻觉化的根本原因。

### 运维记忆

团队更替是传统 SRE 的隐形杀手——部落知识流失。AI SRE 将运维手册 + 事后分析存储在向量数据库中；智能体在每个新事件中检索。当新工程师加入时，AI 拥有完整历史。

### 预事件预测

MIT 2025 年研究：在历史日志、GPU 温度、API 错误模式上训练的 LLM 能在测试集上 89% 的故障发生前 10-15 分钟预测到。

现实检验：没有执行动作的预测只是仪表盘。运维问题是"当我们预测到时，我们做什么？"预先排空？告警？自动扩展？答案是策略特定的。

### 2026 年产品

- **Datadog Bits AI** —— Datadog 内的托管 SRE 副驾驶。
- **Azure SRE Agent** —— Azure 原生。
- **NeuBird Hawkeye** —— 对抗性评估 + 运维记忆。
- **PagerDuty AIOps** —— 分类 + 去重。
- **Incident.io Autopilot** —— 事件指挥官 + 协调。

### 运维手册即代码

运维手册从 Confluence 页面演进为带结构化章节（症状、假设、验证、行动）的版本化 Markdown。结构化运维手册能更好地支持 RAG 检索。启动任何 AI-SRE 推广时，首先将非结构化运维手册转为结构化。

### 应该记住的数字

- MIT 早期检测：89% 的故障，10-15 分钟提前量。
- 多智能体分类：监督器 +（日志、指标、运维手册）+ 人类。
- 安全自动修复集：重启 Pod、回滚部署、范围内扩展。
- 对抗性评估：两个模型独立；一致=高置信度。

## 练习

1. 运行 `code/main.py`。如果日志和指标智能体不一致，监督器如何解决？
2. 为你的服务定义三个"安全"自动修复动作。为每个提供理由。
3. 编写结构化运维手册模板：章节、必填字段、验证命令。
4. 预测性检测在 12 分钟提前量时触发。你的策略是什么——告警、预先排空，还是两者都要？
5. 论证一个 3 人团队应该在 2026 年采用 AI SRE 还是等待。考虑成熟度、量级、风险。

## 关键术语

| 术语 | 人们怎么说 | 实际含义 |
|------|-----------|---------|
| AI SRE | "值班智能体" | LLM 支持的事件调查 + 协调 |
| Supervisor agent | "编排器" | 将事件拆分为子查询的顶层智能体 |
| Specialized agent | "领域智能体" | 拥有工具访问权限的子智能体（日志、指标、运维手册） |
| Auto-remediation | "AI 自动修复" | 窄范围的预批准动作；不是广范围重构 |
| Operational memory | "向量运维手册" | 存储在向量数据库中供 RAG 检索的事后分析 + 运维手册 |
| Adversarial eval | "双模型检查" | 独立分析；一致=高置信度 |
| NeuBird Hawkeye | "对抗性那个" | 具备对抗性评估 + 记忆模式的产品 |
| Bits AI | "Datadog 的 SRE 智能体" | Datadog 托管的 AI SRE |
| Pre-incident prediction | "早期检测" | 故障预测提前 10-15 分钟 |
