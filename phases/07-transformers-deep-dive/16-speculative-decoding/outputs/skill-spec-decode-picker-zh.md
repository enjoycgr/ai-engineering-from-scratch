# 投机解码选择器（Speculative Decoding Picker）

帮助工程师在经典投机解码（vanilla speculative）、Medusa、EAGLE 和 lookahead 解码之间做出选择，并为特定工作负载调优 `N`（起草长度）。

## 需要收集的输入

1. **验证模型（Verifier model）** —— 哪个 LLM 产出最终输出。模型大小很重要（起草成本必须低于验证成本才能实现加速）。
2. **工作负载类型** —— 代码、聊天、结构化输出、摘要。决定接受率（acceptance rate）。
3. **采样策略** —— 贪心（greedy）、低温度（low-T）、高温度（high-T）、束搜索（beam）。高温度采样会降低接受率。
4. **硬件目标** —— 显存预算决定是否能容纳独立的起草模型。
5. **工程预算** —— Medusa 和 EAGLE 需要微调；经典投机和 lookahead 不需要。
6. **延迟目标** —— 交互式聊天（<500ms TTFT，<50ms 每 token）vs 批处理（吞吐优先）。

## 决策规则

- **快速启动，无需训练**：经典投机解码，搭配同一家族的 1B–3B 模型。典型加速 2×。
- **可以微调**：使用验证模型隐藏状态的 EAGLE-2 或 EAGLE-3。典型加速 3–4×。
- **可以微调但无法运行两个模型**：Medusa（验证模型上的额外 head）。典型加速 2–3×。
- **无训练预算，无可用起草模型**：lookahead 解码。典型加速 1.3–1.6×。
- **批处理为主的服务**：连续批处理（continuous batching）更重要；随着批大小增长，投机收益会下降，因为验证模型已经饱和。
- **高温度或随机采样**：接受率急剧下降。考虑降低 N（2–3）或禁用投机解码。
- **结构化输出（JSON、代码）**：接受率高。将 N 推至 7+ 以获得最大加速。

## 调参

- **N（起草长度）**：从 5 开始。测量接受率。若 α > 0.9，推至 7。若 α < 0.6，降至 3。
- **起草温度（Draft temperature）**：与验证模型的温度保持一致。起草采样与验证不匹配会降低 α。
- **树深度（Tree depth，EAGLE-2 / Medusa）**：3–5 个分支；更宽的树只在 α > 0.8 时才有帮助。
- **起草模型大小**：满足 α > 0.7 的最小模型。70B 验证模型搭配 1B 起草模型是典型配置；不要低于验证模型的 tokenizer / embedding 兼容性要求。

## 必须标记的注意事项

- 确认起草模型和验证模型共享同一个 tokenizer。不同的 BPE 分词会破坏投机解码的保证。
- 投机解码与 vLLM 的连续批处理存在交互：当批处理已经饱和时，每个请求的加速会下降。
- EAGLE 的隐藏状态输入需要访问验证模型内部；并非总是通过 HF API 暴露。优先使用 vLLM 或 SGLang 运行时。
- Medusa head 需要对验证模型自身输出进行监督微调。数据收集步骤通常是主导成本。

## 输出格式

返回：

1. **推荐方案** —— 一个策略名称及调参（例如 "EAGLE-2, N=5, tree_depth=4"）。
2. **预期加速比** —— 附带明确的 α 假设。
3. **兼容性检查** —— tokenizer 匹配、运行时支持、KV cache 回滚支持。
4. **回退方案** —— 若主策略表现不佳，下一步尝试什么。
5. **测量计划** —— 如何在代表性样本上验证接受率和加速比。
