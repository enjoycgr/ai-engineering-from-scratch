# 高级 RAG 范式

基本 RAG：嵌入查询 -> 向量搜索 -> top-k -> 生成。
高级 RAG：嵌入查询 + BM25 -> 融合排名 -> 重排序 -> top-k -> 生成。

```
query -> [vector search (top-50)] -+-> RRF fusion -> reranker (top-5) -> prompt -> LLM
                                   |
query -> [BM25 search (top-50)]  --+
```

## 何时从基本 RAG 升级

- 检索质量下降到 Recall@5 低于 70%
- 用户报告错误或无关回答
- 语料库增长到超过 100K chunk
- 查询使用与文档不同的词汇
- 多跳问题持续失败

## 实现检查清单

1. 在向量索引旁边添加 BM25 索引
2. 并行运行两次搜索（各 top-50）
3. 用倒数排名融合（k=60）合并
4. 用 cross-encoder 重排序 top 候选者
5. 取 top-5 用于最终提示
6. 在测试集上添加忠实度评估

## 技术选择指南

- **混合搜索**：生产环境始终使用。查询时无额外成本。
- **重排序**：当 Recall@50 好但 Recall@5 差时使用。增加 50-200ms 延迟。
- **HyDE**：当查询模糊或使用与文档不同的词汇时使用。增加一次 LLM 调用。
- **父子 chunk**：当小 chunk 缺乏上下文但大 chunk 稀释相关性时使用。
- **元数据过滤**：当语料库有明确类别（日期、来源类型、部门）时使用。
- **查询分解**：用于需要从多个文档获取信息的多跳问题。

## 常见错误

- 用不同的 chunk 集运行 BM25 和向量搜索（它们必须搜索相同的语料库）
- 重排序的候选池太小（top-10 太少；使用 top-50）
- 为每个查询添加 HyDE（只在词汇不匹配是瓶颈时才有帮助）
- 不评估变更（在添加每种技术前后测量 Recall@k）
- 在测量故障位置之前过度工程化流水线

## 评估工作流

1. 创建 50+ 个带有已知答案 chunk 的测试问题
2. 为每种检索方法测量 Recall@5 和 Recall@10
3. 对于检索成功的查询，测量生成回答的忠实度
4. 随着语料库增长每周跟踪指标
5. 在添加更多技术之前调查个别故障
